# bloom-biorxiv — working standards

Review record for the "Development scaffold: design for review" proposal (distilled from
Cherimoya and RegRex), resolved for this project on 2026-11-12. Each item states the scaffold's
default, our decision, and what it binds. Changes here must be reflected in `AGENTS.md`,
`CONTRIBUTING.md`, `pyproject.toml`, `.pre-commit-config.yaml` and CI.

| # | Scaffold default | Decision | Project-specific resolution |
|---|---|---|---|
| 1 | One shared `AGENTS.md`; `CLAUDE.md` imports it | **Keep** | `AGENTS.md` = repository map, commands, contracts (tensor shapes, index spaces, seeds), coordination rules, numerical gotchas (seq-head scale, padding mask semantics, L=8192 memory). `CLAUDE.md` is one line: `@AGENTS.md`. Same pattern as `bloom-manuscript`. |
| 2 | Ownership + interfaces for parallel work; one integrator | **Keep (scaled)** | Phases 2 (ATAC) and 3 (internals) can run in parallel after Phase 1; each parallel task gets its own worktree **and its own conda env** (`scripts/setup_env.sh <name>`), owns a disjoint path set (listed in the issue), and agrees on `tokens.py` / `ViewStrategy` / `EncodeOutput` signatures before starting. Rohan is the integrator and owns `pyproject.toml`, `AGENTS.md`, CI config. |
| 3 | One `main`, short `<type>/<desc>` branches, focused PRs, squash merge, Conventional Commits | **Keep** | Never commit to `main` (as in `bloom-manuscript`). Types: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `chore`, `ci`, plus project scopes `(prepare|strategies|model|internals|assets|cli)`. `!` for breaking changes to the output schema or CLI. Enforced by review first; a commit-msg hook only if it slips. PR body: problem → result → validation evidence (which test tier ran, on which device). |
| 4 | Python 3.12, `uv` + committed `uv.lock`, Hatchling, `src/bloom_biorxiv/`, runtime deps torch + Lightning | **Change** | Python ≥ 3.12, Hatchling, `src/bloom/` (import name `bloom`, as decided). **No Lightning, no Hydra** (decided). **No lockfile and no `environment.yml`**: `pyproject.toml` is the only dependency file. PyTorch is the reason — its build is accelerator-specific and parallel tasks need separate environments — so the documented path is: create a conda env → install the PyTorch build for your platform → `pip install -e .[dev]`; `scripts/setup_env.sh <env> [cpu\|cu128]` automates it (`uv pip install` inside the conda env is allowed and faster, not required). CI pins the CPU torch wheel explicitly. `bloom-arch` is a pinned git tag. |
| 5 | Fast pre-commit (Ruff + file checks), `scripts/check.sh`, one CI job; expensive tests by explicit selection | **Keep** | pytest markers `unit` / `regression` / `assets` (test-plan.md). `scripts/check.sh` = `ruff check` + `ruff format --check` + `pytest -m "unit or regression"`. CI = the same on CPU, plus `pip install -e .` from a clean env. `assets` tier (downloads, GPU, 5.4 GB peak table) runs manually on the maintainers' GPU host before a tag; its results go in the PR/release notes. Ruff config carried over from `alleninstitute/bloom` (`I, N, NPY, RUF`; `\u` escapes instead of non-ASCII in strings). |
| 6 | Test scientific contracts, not just execution | **Keep** | test-plan.md is the contract list: parity vs reference embeddings (G1–G8), masking/padding invariance (S8–S9), seed semantics (S4), batch-size and device invariance (G7–G8), internals shapes and `pair_logits` correctness (I1–I7). Every behaviour change to `model/`, `strategies/`, `tokens.py` or `prepare.py` must add or update one of these, with a stated tolerance. Every output records provenance (`uns["bloom"]`: model sha, strategy, seed, device, precision, versions). |
| 7 | One narrowly scoped skill | **Keep** | `.agents/skills/embedding-parity/SKILL.md`: how to validate a model/strategy change — which regression tests, tolerances, how to regenerate reference embeddings with the original `evaluate.py` on the maintainers' host, how to run the `assets`/GPU tier, what to paste into the PR. A `publish-assets` skill is added when Phase 0 is executed a second time. |
| 8 | Lightweight docs: README, CONTRIBUTING, AGENTS, `docs/architecture.md`; review via PR evidence | **Keep** | `docs/architecture.md` is the maintained successor of SPEC.md; DATA_SCHEMA / ASSETS / TEST_PLAN / STANDARDS move to `docs/` as-is. Markdown only in v1; **MkDocs + GitHub Pages is a roadmap item** after the main functionality lands. Notebook conventions (outputs committed vs stripped, CI execution) are **deferred** to the roadmap. Maintainer merges; a second human review when available. **Review is use-case driven**: the reviewer (human or agent) exercises the end-user paths — the bioinformatician's `bloom embed` on their own h5ad and the ML user's `encode(return_internals=True)` / custom `ViewStrategy` — rather than reading diffs line by line, and files what it finds as GitHub issues with `gh issue create` (one issue per finding, labelled `use-case:bioinformatician` / `use-case:ml`, with the exact command or snippet that was run and what was expected). Issues, not PR comments, so findings outlive the PR and can be triaged into phases. |
| 9 | Let the application determine its abstractions; no pre-built registries/frameworks | **Keep, with two named exceptions** | No model registry, no config framework, no tracker integration, no cloud SDK beyond asset download. Two abstractions are created up front because they are product requirements, not speculation: the `ViewStrategy` ABC (the stated extension point for ML users) and the dataclass `ModelConfig` serialized to `config.json` (needed to load weights without the training repo). Datasets, downloaded assets and outputs stay outside Git (`~/.cache/bloom`, `tests/data/` fixtures excepted). |

## Other preferences and additions

| Preference or requirement | Reason | Files / workflow affected |
|---|---|---|
| Type hints required on the public API (`bloom.*`, dataclasses, `ViewStrategy`); Ruff only, no type checker in CI | Hints document tensor shapes and index spaces for the ML user; a checker's torch/anndata stub noise is not worth it at this size | `pyproject.toml` (ruff), `CONTRIBUTING.md` |
| Tensor-shape comments on every public tensor (`# (B, L, 1024)`) and index-space suffixes in names (`emb_idx`, `col_idx`) | The two index spaces (dataset column vs reference row) were the main source of bugs in the training repo | `AGENTS.md` contracts section |
| Determinism contract: `top`/`panel` bit-reproducible across batch size, workers, device (CPU/GPU within 1e-3); `resample`/`tile` reproducible given `(seed, cell_index)`. Regression policy (2026-11-13): `top` gated vs Phase 0 references — CPU fp32 / GPU TF32-off `max |Δ| < 1e-4` vs `*_tf32off`, GPU vs CPU `< 1e-3` with `encode` unfused on CUDA (v0.1.0, #44; the paper-faithful fused-kernel refs are a sanity check only); `resample`/`tile` statistical parity only (mean cosine > 0.999, kNN ±1 pt); stricter gates once the code stabilises | Users compare embeddings across runs and machines; TF32 noise floor of the original pipeline is ~2e-4 | test-plan.md S1, S4, G1–G5, G7, G8 |
| Code MIT (`LICENSE`); weights, reference tables, example data and model card CC BY-NC 4.0 (model card, bucket README, `MANIFEST.json` `license` fields, README "License") | Decided 2026-11-13 (#10) | repo root, `tools/bucket/MODEL_CARD.md`, `tools/make_manifest.py` |
| GPU test hardware: the maintainers' Linux host (1× NVIDIA L4 24 GB); no GPU CI | Only GPU available; the `assets` tier is manual | `CONTRIBUTING.md`, `docs/maintainers.md`, skill `embedding-parity` |
| Release = git tag `vX.Y.Z` + GitHub release notes (no archival DOI for the bioRxiv releases; one accompanies the publication); assets versioned independently via `MANIFEST.json` | No PyPI for now | `CONTRIBUTING.md`, `assets.py` manifest pin |
| Experiment-style scripts (`tools/`) are not installed and not tested in CI; they must print the asset sha256s they produce | They run on the cluster against private paths | `tools/`, assets.md |
| Reviewer tooling: `gh` CLI is the review interface (`gh pr checkout`, `gh issue create`, `gh issue list --label use-case:*`); reviewer has triage permission on the repo. Issue template `use-case.md` asks for: user persona, command/snippet run, expected vs observed, data shape (cells × features, species, modality). Labels: `use-case:bioinformatician`, `use-case:ml`, `phase:1..4`, `roadmap`. | Findings framed as end-use failures are actionable across phases; `gh` keeps the reviewer out of the web UI | `.github/ISSUE_TEMPLATE/use-case.md`, repo labels, `CONTRIBUTING.md` (review section), `AGENTS.md` (reviewer role) |
| Agent reviewers running where `gh` cannot verify TLS (sandboxed macOS) use the GitHub REST API with the same issue template body | Known `gh` limitation in the sandbox used here | `AGENTS.md` note |

## What this means for the first commits

1. `AGENTS.md`, `CLAUDE.md` (`@AGENTS.md`), `CONTRIBUTING.md`, `LICENSE`, `README.md` (quickstart placeholder).
2. `pyproject.toml` (hatchling, `src/bloom`, console script, `[dev]`, ruff config), `.pre-commit-config.yaml`,
   `scripts/setup_env.sh`, `scripts/check.sh`, `.github/workflows/ci.yml` (CPU: install + check.sh).
3. `docs/` with these five documents (`architecture.md` = SPEC).
4. `.agents/skills/embedding-parity/SKILL.md` (stub pointing at TEST_PLAN §5 until Phase 0 produces references).
5. `.github/ISSUE_TEMPLATE/use-case.md`, the `use-case:*` / `phase:*` / `roadmap` labels, and a `CONTRIBUTING.md` review section describing the use-case-driven review loop (`gh pr checkout` → run the user paths → `gh issue create`).
